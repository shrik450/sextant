## What didn't hold

- Added files doubled on screen (above): the waste was real, the visible doubling wasn't.
- "`--cc`" as an option for unmerged files: git prints no combined patch with `--raw -p`, even with `--cc`.
- "NUL-separated I/O throughout": not possible for hash-object; C-quoting is git's own way in.
- `git diff HEAD` (the uncommitted target, the default) never emits combined headers; only the unstaged target (`git diff` against the index) did. Staged (`--cached`) gives plain `U` entries, which already showed as "Unmerged".

## What the next step must know

- `hashObjects` returns `[String?]`; nil means unhashable (folder, nested repo, unreadable, gone). Callers must handle it.
- `RawChange.status == "U"` can now have hunks (an unmerged file against our side). `emptyNotice` still says "Unmerged" when it has none.
- Patches pair to raw entries by path. Anything new that runs `git diff` through `parseRawPatchZ` must keep `--src-prefix=a/ --dst-prefix=b/` (they're in `Git.diffFlags`).
- `readWorktreeFile` returns a symlink's target path, never its target's contents. DefinitionIndex and Explore get that for symlinks now.
- Leads for later, not done:
  - Paths are decoded as UTF-8 throughout (`String(decoding:)`), so a non-UTF-8 file name (patho has a Latin-1 one) can't be found again on disk: untracked ones now drop out of the worktree diff (before, they failed it). Paths need to stay bytes end to end.
  - A change of line endings alone reads as identical removed/added lines; a note ("Line endings changed") would say why.
  - An untracked file deleted between hashing and reading shows "Too large to show" until the next refresh.
  - The review's commit list still stops at 1,000 without saying so.
  - In-process symlink hashing assumes SHA-1, as the rest of the app does (zeroOid, emptyTreeOid).
- 1e: FileState's "no hunks means whole" rule (pure renames, mode changes) now lives in `FileDiff.hunksAreWholeFile`, which `Repository.open` also uses. Change it there.
