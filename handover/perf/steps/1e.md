## Item 2: the run identity

Full picture: a run's key was `fileReviewKey#hash(run lines)`. Identical runs collided (reproduced: one key, and reading the first reviewed the file). Worse for the stated goal: `reviewKey` includes the new blob ID, so **any** edit anywhere in the file (an agent working) unread every run in it, and reviewing a file cleared its runs, so after an agent touched a reviewed file everything in it was unread again.

What I chose:
- **A run's key = FNV-1a of its lines (kind, text, endings) + its occurrence number among runs with the same lines** (`hash`, `hash-1`, …). It's the same in hunks and whole file, survives any edit elsewhere, and changes only if the run itself changes or an identical run appears/disappears before it. I considered the neighbouring lines: they add nothing to stability (a run's immediate neighbours are context lines; editing one extends the run), and they aren't reliably in the hunks, because **a user's `diff.context=0` reaches Sextant's diffs** (checked), leaving hunks back to back. Runs also now end at a gap between hunks (`changeRuns(_:gapsBefore:)`), which that case needs for hunks and whole file to agree.
- **Reads are kept by the file a change starts from**, `RawChange.readingKey` = old blob, old mode, old path, path (no new side), and **reviewing a file records its runs read**. So when an agent edits a reviewed file elsewhere, it's no longer reviewed, but only the new run is unread (scene `read`). Unreviewing clears the file's reads. `!all.isEmpty` is now required before reading a run reviews the file.
- Storage: hard cutover. `read.json` became a map (now `{readingKey: {owner, keys}}`); old arrays fail to decode and start empty. Each file is written only when it changed (was: both files every time).

## Bounding read.json (orchestrator, on 3a78203)

Done rather than argued: 3dbb389. Reads are shared by every review in a repository (the same change shows in a commit, a range and a branch review), so pruning against one review's diff would delete others' reads. Each entry names the review that last read in it, `Review.readingOwner` = subject key + the part read (`everything`, `uncommitted`, `staged`, `unstaged`, `commits:oldest..newest`), deliberately without the base or resolved commits, so a branch or worktree review keeps owning its reads as they move. When a review's changes load (`apply`, successful diffs only), entries it owns whose starting file isn't in the new diff are dropped, without a change notification (nothing showing displays them). The `read` scene checks that committing the work empties read.json.

Measured (release, `bench-readjson.txt`), a 10,000-file review, 5 runs a file, fully reviewed, after its base moved 20 times:

| | entries | read.json | load | write (on every toggle, on main) |
|---|---|---|---|---|
| without the prune | 200,000 | 59 MB | 650 ms | 723 ms |
| with the prune | 10,000 | 2.9 MB | 25 ms | 27 ms |

What stays unbounded: a scoped commit view's reads (its diff never changes, so it never prunes; bounded by what was reviewed) and **`reviewed.json`, which has always kept every transition ever reviewed** (200k keys in that run). Step 3 (persistence off main) should cap or compact both, and stop pretty-printing; 2.9 MB written on each `r` in a fully reviewed 10k-file review is still too much on main.

## Perf leads, measured for steps 3 and 6 (not fixed)

Instrumented release build (timings to stderr, uncommitted), `many` (10,000 files, 450k rows), 100 notes anchored across files, All Changes, three Mark File as Reviewed (`measure/overview/`):

- **reviewsChanged: holds.** `refreshReadState` takes **28–47 ms** per toggle: 10,000 `recolor(file:)` calls, each with its own `colorVisibleRows`, of which only 22–52 `isRead` lookups actually happen (visible rows). Then the overview's `reload(keepPosition: true)` takes **2.71 s** per toggle (of which `layoutRows` 34 ms), though nothing in the text depends on review state: this is step 3's "review toggle without text replacement", and the dominant cost of the overview's 3 s mark-reviewed budget miss.
- **layoutRows O(F × notes × L): holds in form, negligible in cost.** 34–38 ms for 10,000 files and 450k rows with 0 or 100 notes; the notes part is lost in the noise. After 1450ca7 `anchor(of:)` is O(1) per matching file; what's left is a path compare per file per note (1M compares at 100 notes). Pre-grouping notes by path is still worth doing in step 3, but it isn't where the time goes.
- **reviewKey String per access: holds, negligible.** ~0.7 µs per `isRead` (including `run(at:)`'s linear scan), only for visible changed rows (colouring and each `drawBackground`): ~35 µs a frame at 50 rows. Since 3a78203 each lookup builds two strings (`reviewKey` and `readingKey`); caching both on `RawChange`/`FileState` would make it allocation-free if step 3 wants it.
- **Up to 6 parses for one file: holds, and it's 7.** A two-file repository (`measure/parse-*`), counting `SyntaxLanguage.parse` calls by text length:
  - Opened directly in a file pane, caret landing on a name: **4 parses** of the file (each side twice: `analyze(symbols: true)`, then names), plus 2 of the neighbour `prepareNeighbors` analyses.
  - Opened from All Changes: **7 parses** of the file: both whole sides analysed for the overview without symbols (the first file is read whole at open), again with symbols when opened (ContentAnalysis caches tokens without definitions and discards them), names on both sides, and one more on the new side. Step 6's single parse with demanded outputs removes all but one per side.
