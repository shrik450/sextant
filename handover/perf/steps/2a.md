## Commits

- **6ac0f0f Stop a cancelled git and what it started, and bound what each git may print (item 1).** `runProcess` (SextantCore/Subprocess.swift) `posix_spawn`s in a process group of its own, *suspended* (`POSIX_SPAWN_START_SUSPENDED`) until its exit source is installed, then reads stdout/stderr and writes stdin through dispatch sources: no thread waits on git. Cancellation sends SIGTERM to the group, SIGKILL a second later, and a stopped run SIGKILLs what's left of its group when the leader is reaped; the task throws `CancellationError` once git is reaped. Every caller passes `limit:` (`Git.Limit.value` 1 MB, `.listing` 256 MB, `.patch` 512 MB, `.blob` 256 MB); past it, git is stopped and the run throws `GitError` with `reason == .outputTooLarge(limit:)`, never part of the output. stderr keeps 64 KB. `oldLines(of:limit:)` and `blob(_:limit:)` take limits. `listPullRequests` runs `gh` the same way. `RunningProcesses.count` counts live runs.
- **6c5533a Read every checkout's status without tripping a Swift optimizer bug (step 0's blocker).** See "Baseline".
- **7df36da Share one blob reader per repository, and end it when idle or unused (item 2).** A `Git` holds its `ObjectReader`; `git.forCheckout(root)` gives another checkout of the same repository the same reader (used by the resolver for worktree reviews and by `statuses(of:)`). The process starts with a read, ends after 20 s idle, and ends with the last `Git` holding the reader (deinit). It's spawned through `spawnProcessGroup` with only its two pipe ends open. Bodies are read through a fixed 64 KB buffer into `Data` reserved at the blob's size. A blob over the caller's limit is skipped (or the process restarted past 16 MB) and throws `outputTooLarge`. A cancelled read that hasn't started throws `CancellationError`; one in progress finishes.
- **982ce66** A timing fix to 7df36da's idle test (200 ms idle could end before the test looked under a full run).
- **fcac27f Prepare only the next file in the reading direction, within a budget (item 3).** See below. Adds `SharedWork` (SextantCore) and the `neighbours` scenario (full tier).
- **3daf053 Stop what a review or pane started once nothing shows it (item 4).** Scenes `drop`, `slowdrop`, `paneclose`; dump fields `readers`, `processes`.
- **10f9999 Keep what nothing shows within one budget of bytes, dropping the oldest (item 5).** `MemoryCache` / `UseOrder`; dump field `cacheMB`.

## Baseline (task 0)

`run.sh --out baseline/full-step1 worktrees soak linux`, then the quick tier, at 2208911 while the user was away. **The forward guard never fired**: all 24 `came_forward`/`beeps` rows are 0, here and in every later run this step (every launch). I didn't touch the guard.

**worktrees didn't run, and it wasn't the guard: the release app crashed.** SIGSEGV (exit 139, no crash report written) in `AsyncTask::completeFuture` 1.3 s after opening any repository with **two or more linked worktrees**, deterministically. Tracked down with a `DYLD_INSERT_LIBRARIES` backtrace dylib, then by bisecting the fixture (0 or 1 linked worktree: fine; 2: crash), then a release-mode test: `Repository.refreshStatus`'s task group returned **0 of 3** statuses every time. It's a **Swift 6.3.3 optimizer bug**: a group child of the shape `let checkout = Git(...); do { return (root, .success(try await checkout.status())) } catch { ... }` loses the group's results and corrupts memory, in release only. Binding the status to a local first, inlining the `Git(...)`, or a same-module stand-in type all work (`miscompile-repro.swift.txt` has the variants). It came in with 1c's 38ab8fc (status started throwing); 1c ran only the quick tier, which never opens several worktrees. Fix: `Git.statuses(of:)` in SextantCore, written in the shape that compiles right, with an integration test that fails in release (1 of 5, then an abort) on the old shape. **Our tests run in debug, where this passes either way**; only a release run (`swift test -c release -Xswiftc -enable-testing`) or the GUI tiers catch it. It may be worth reporting upstream.

## Item 1: Git.run

Verified as described: no cancellation handler, unbounded stdout, 2–3 parked threads. Also found: **stdin was written with a plain `FileHandle`, so a git that exits before reading all its input (more than a pipe's worth) killed the app with SIGPIPE.** Reproduced with the old pattern (`sigpipe/`): `hash-object --stdin-paths` with a missing first path survives 1,000 paths and dies (exit 141) at 100,000. In the app that's a large untracked burst with one unreadable/vanished path.

Measured (`threads/`, 64 gits each sleeping 1–3 s, with `sample` mid-wait):

| | old Git.run | runProcess |
|---|---|---|
| threads half-way | 91 | 32–50 |
| threads blocked in read/waitpid | **90** | **0** (all idle in `workq`: GCD's pool, grown by the burst of spawns) |
| total time | 1.13 s | 1.08 s |

Tests (`ProcessTests`, real gits through shell aliases): cancelling stops git, its shell and the shell's `sleep` in under 0.9 s; a shell trapping TERM is killed within ~1.4 s; a task cancelled first runs nothing; output past the limit is an error; 200 runs at once each get their own output; a git that stops reading 6 MB of input fails the run alone.

**Getting this right took two goes** (`loop-*.txt`): a process exit dispatch source registered after the child exits never fires (and its registration handler doesn't run either), and on NOTE_EXIT `waitpid(WNOHANG)` can still return 0. Both hung ~40% of test runs. The child now starts suspended and gets SIGCONT from the source's registration handler, and the exit handler waits (blocking, a moment) for an exiting child. 30/30 and 10/10 loops clean since, and 193–205 tests in every full run.

## Item 2: ObjectReader

Held: app lifetime, keyed per root (a worktree review and the repository each ran a cat-file over the same objects), three copies per blob.
**The fd lead held, as a leak on restart** (`oldreader/`, the old class verbatim): 4 → 8 descriptors on start (each pipe end dup'd, originals left with the `Process`), then **+3 on every stop and restart** (8, 11, 14, 17), never given back. New reader: 2 while running, 0 when idle, process gone when the reader goes.
Copies, reading a 64 MB blob 5×: old 12–13 ms per read, **peak RSS 135 MB**; reading straight into a fresh `Data` 16 ms / 86 MB (page faults on fresh pages cost more than a copy); through the warm buffer into reserved `Data` (committed) **14–15 ms, 70 MB**.

## Item 3: neighbours

Held. Before: i+1, i−1 and i+2 read whole and analyzed, uncancelled, any size. Now one neighbour in the reading direction (backwards when the pane last opened a later change), old side read with a 1 MB limit and analyzed only if neither side passes 1 MB (`RepoWindowController.neighbourBytes`), cancelled by the next step. Reads, analyses and name indexing are `SharedWork`: one run for everyone waiting; a cancelled waiter stops waiting at once; the run is cancelled when the last waiter goes. A read that finds the old side over its limit records that, and a caller with a larger limit reads again.

`neighbours` scenario (open `longline.swift`, whose neighbours are megaline/million/minified, sit 15 s, step back): **before, killed at 4 GB about 6 s after arriving; after, footprint −17 MB, 232 ms CPU, 46 ms after stepping back.**

## Item 5: one byte-bounded LRU

`MemoryCache.shared` (64 MB) owns whole texts (FileState holds them weakly; a pane showing one keeps it) and ContentAnalysis's blob analyses (replacing `RecentlyUsed`, which counted tokens and searched for the oldest in O(n)). `UseOrder` is O(1) (linked list in arrays); its unit test checks 20,000 random operations against a naive list.

**The soak and Linux scenarios don't measure this** (`cache-before/`, `cache-after/`, `census/`): soak footprint at 100 cycles 130 → 141 MB and heap 59.7 → 59.7 MB; Linux reading-end 333 → 346 MB at the mark. Heap censuses show why: at Linux's `files-read` mark the footprint is 282 MB but 4 s later 161 MB with a **live heap of 66 MB** — the scenario's MARK footprints are mostly transient parse memory malloc hasn't returned — and the soak's growth is AppKit's (1a). What the cache bounds only shows in a long session, so I measured one (`census/long.sh`: 500 Next File steps through Linux HEAD~30..HEAD, heap at every hundred):

| heap at 100 / 200 / 300 / 400 / 500 files | read time |
|---|---|
| 3daf053: 127, 163, 210, 272, **312 MB** | 275 s |
| 10f9999: 126, 138, 139, 142, **142 MB** | 215 s |

A bug the first long run found: a text larger than the budget was refused by the cache, freed at once (only a weak reference held it) and read again in a loop. The newest value is now kept alone even over budget until the next one comes, and `loadWhole` stops after one read.

## What didn't hold, or differed

- The forward guard didn't misfire once; the blocked runs this time were the release crash above.
- "Parks 2–3 threads per process": 2–3 *threads* per run, but GCD caps them, so 64 runs parked 90 rather than 192.
- ObjectReader's dup: not a steady leak while running (4 descriptors, not 2) but +3 per restart, permanently.
- Reading a blob without copies was slower than one copy into a warm buffer (page faults); kept one copy.
- Item 5's soak/Linux before/after: no change, because neither holds memory in these caches (above). Session.explored is bounded through the whole texts it holds; the `FileState` shells stay (small).
- 1c already stopped a closed pane's reader (`stopWork`), but the analysis it awaited wasn't cancellable, so the reader lived until the parse ended.

## What the next step (2b) must know

- **Limits to hang admission on**: `Git.Limit` (one place for patch/listing/blob bounds), `GitError.reason == .outputTooLarge(limit:)`, `ObjectReader.blob(_:limit:)` (reads only the header for an over-limit blob), `FileState.loadWhole(git:limit:)` (`WholeRead.tooLarge`, `largerThan`), `RepoWindowController.neighbourBytes`, `FileText.largestSide`, `MemoryCache.shared` budget. `contents(of:in:)` still reads the worktree with `readWorktreeFile`'s 4 MB default and index/commit blobs with `Limit.blob`: unify them with the preview limit.
- **Cancellable parsing**: a cancelled `SharedWork` run cancels `FileText.analyze`'s task and its `async let` sides, but `ContentAnalysis.analysis` awaits a detached task that runs `language.analysis` to the end. Make that run a `SharedWork` per key (as `FileText` does) and have the parse check cancellation (ts_parser cancellation flag or timeout); then `paneclose`'s parse stops too.
- **ObjectReader** reads are serial and uncancellable once started; a 256 MB blob blocks every other read for the time it takes. Step 7's reader pool and 2b's admission both live here.
- Hunk texts (`FileState.hunks`) and their analyses stay with the session: in the overview they're all shown. Step 3 (overview work bounded by what's visible) is where they can become evictable; the cache's weak-owner pattern (`FileState.whole`) is the model.
- `MemoryCache` counts a blob analysis and a FileText built from it separately though they share token buffers, so it overcounts (safe: real memory stays under the budget).
- `Git(root:executable:)` makes a new reader; use `forCheckout(_:)` for another checkout of the same repository.
- Session loads now live in `Session.loads` and stop with `stopWork()`; a refresh's `load(s)` still doesn't cancel an earlier one for the same session (step 4's coordinator).
- **Run release tests** before trusting concurrency-heavy code: `swift test -c release -Xswiftc -enable-testing` (it builds in ~30 s). The Swift 6.3.3 miscompile passes every debug test.
- Commits are unsigned (1Password isn't reachable from these sessions), as before.
