## Item 1 in context

Only builds without `SextantGitPath` read the login shell on the way to git: the release (Homebrew) build. The nix package and every benchmark and scene bundle set it, so no launch measurement ever saw the wait. Here fish takes 29–33 ms; with a heavy profile, or a profile that leaves something holding stdout, the old code blocked the main actor for seconds, or until that program exited. A no-git bundle (probe/nogit) opened a repository and found git on the shell's PATH through the new code. I kill the shell's group only at the deadline: a program a profile starts in the background after a normal exit (an agent, say) is left alone, and now holds nothing up.

## Item 2: what held

- **The spin didn't hold.** The old command used 0.00–0.01 s of CPU over a 0.95 s open, timed against a background-only stand-in app (a native binary that sleeps; the stand-ins were unregistered and deleted). With NSWorkspace's request in flight the run loop has a source and sleeps. Argon's harness had no NSWorkspace call. The command waits in a continuation now anyway.
- **Held:** `--staged`/`--cached` refused (`unknown revision: --staged`); a file refused (`README.md` read as a revision, `./README.md` as "not a directory"); a lone name that's a folder and a branch read as the folder, silently (by the code; I didn't run the old command on it, since it would have opened an app).
- **Didn't hold as stated:** `A..` and `..B` weren't refused; the empty side was skipped, so HEAD wasn't checked. They're checked now.
- **Sequential stdout/stderr reads:** real, but `rev-parse` never fills a pipe. Gone with `Git.run`, which also clears `GIT_DIR`/`GIT_WORK_TREE` and sets `GIT_OPTIONAL_LOCKS=0`.
- **A decision:** a lone argument that's both a revision and a path is an error naming both ways out (`./docs`, `sextant . docs`), as git does, rather than quietly preferring one. The app's words (`staged`, `#12`, …) always mean revisions.
- The binary grows from 103 KB to 2.4 MB (SextantCore brings SwiftTreeSitter). A small core target without tree-sitter would avoid it, if that matters.

- **Every key goes through the event queue** (`postEvent` then `nextEvent`), so `NSApp.currentEvent` is the key while it's handled, as with a keyboard. Calling `sendEvent` alone left a stale event there (probe: type 13, never the key).

Scripts never used `key` for menu commands (they use `menu`), so no earlier number depended on it.

## Bare keys (item 5)

Ground truth from a probe that logged `NSMenu.performKeyEquivalent` (probe/keys): AppKit's `NSApplication` event routing offers **every** key to the main menu before the window gets it, bare `u` in the file filter included. So the guard is needed. The old one disabled every bare-key command whenever the repository window's first responder was editable text: greyed in the menu bar, missing from Go to Anything opened from a filter, and blind to panels. With Go to Anything (key, never main) opened from the reader, AppKit validates through the main window's controller, whose first responder is the code view, so typing `u` ran Next Unreviewed File and the field stayed empty (scene `fields`, through the harness's routing; **not tried on a real keyboard**, since GUI runs stay behind the windows in use). Now `isTypedIntoText` refuses a bare-key item only while the current event is a bare key-down whose window's first responder is editable text. Copy Symbol Name validates on `symbolAtCaret` (Argon was right: a blank line in a function had Copy Symbol with Reference enabled and Copy Symbol Name not). `fields`: 5 of 7 checks fail on the old guard.

Not done (step 3): `validateMenuItem` per-item cost (`commitRows`, `actionPaths` filters, `keyedRuns`), 12–100 ms per Go to Anything at Argon's scales. The dump now calls `enabledCommands` (one validation per menu item) for its `commands` field.

## reviewed.json (item 8)

Each reviewed transition names the review that last reviewed it (`reviewed: [reviewKey: owner]`), and a review's prune, on each successful load, drops what it owns but no longer shows. What it shows includes **its commits' changes**, since the commit list shows each commit's progress (Mark Commit as Reviewed records under the review showing it); read entries now keep those starting files too. Hard cutover: an old `reviewed.json` array doesn't load, so **existing reviewed marks are dropped once** (as 1e did for read.json).

Release benchmark, 1e's shape (10,000 files, 5 runs each, fully reviewed, base moved 20 times; `bench-reviewed.txt`):

| | keys | reviewed.json | write | load |
|---|---|---|---|---|
| before | 200,000 | 32.5 MB | 154 ms | 94 ms |
| after | 10,000 | 1.9 MB | 10 ms | 11 ms |

read.json unchanged at 2.9 MB / 27 ms. Scene `read`: committing the work now empties reviewed.json too (the old app kept the transition).
