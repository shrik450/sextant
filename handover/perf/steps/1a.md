# Step 1a: the row-view leak and the main-thread hangs

Branch `perf`, 5 commits on 7fc00ee. Results are in `scratch/perf/step1a/` (copied from the worktree's `scratch/perf/step1a/`). Tools I wrote for this step are in `step1a/tools/` (leak probe, census bisect, spin probe, minified sampler) and `step1a/purgatory/` (standalone AppKit probes).

## Commits

- **98c17f9 Find names in one pass over a line and its tokens.** `forEachIdentifier(in:range:tokens:_:)` walks the line once in 4,096-unit chunks (`getCharacters`, no per-unit message send), checks ASCII by range, and caches `CharacterSet.alphanumerics` once for the rest. Skipped tokens are checked with `OrderedIntersections`, which is one pass over the tokens sorted by location (sorted once if they aren't). `identifiers(in:tokens:)` is built on it. Landing, word steps (`stepName`) and `identifier(at:)` read the code view's string in place, without `attributedSubstring`. Landing and stepping stop at the name they want. Landing also stops once it has passed every changed range. Tests: a differential test against the old quadratic code (3,000 random lines with overlapping, unsorted and empty tokens, digits, non-BMP characters and surrogates), every UTF-16 unit against `CharacterSet.alphanumerics`, chunk boundaries, and `identifier(at:in:)`. A mutation (`>` to `>=`) fails 571 checks.
- **b24b25b Keep side-column work waiting for a file until it shows, not spinning.** Work that comes due while the focused pane loads is parked in `waitingForFile`, with `busy` held once. `Pane.showGeneration` and `loadingGeneration`, and the window's `focusedPane`, call `runWorkWaitingForFile()` when they change. That reschedules the parked work through `afterFrame`, so it still runs after the file's frame, and it parks again if the pane started another load in between.
- **8fd4a2a Count only row view objects in the soak.** heap lists `PillRowView` twice: once for the objects and once for `PillRowView._columnViews (id[])`. The driver summed both lines. **Every soak row count before this commit is about double** (step 0's 241 → 1,613 is really 117 → 803).
- **b0a9dd0 Give side-column lists back the rows they removed.** This is the leak fix (cause below). The look makes fresh row views again. Each list (Files, Find, Inspector) has a `RowViews`, which keeps the rows `outlineView(_:didRemove:forRow:)` reports and hands them out before making new ones.
- **6506d06 Change the inspector's model with each update it tells the outline of.** `merge` now updates inside one `beginUpdates`/`endUpdates`: first the children without those removed, then `removeItems`, then the fresh children, then `insertItems`. Separate commit, because it wasn't part of the leak (below).

## The leak: why reusing by identifier wasn't enough

The census builds count live row views through init/deinit and read each table's private `NSTableRowData` ivars (temporary instrumentation, not committed). They showed this:

- Before: the rows that survive are hidden subviews of one outline (its `_subviews`). Every `PillRowView` has its own `NSISEngine` (through `_layoutAux`), so engines grow one for one with rows.
- Reusing by identifier (`makeView(withIdentifier:)`, as asked): growth falls from about 54 rows per cycle to about 8, but doesn't stop. The leftover rows are detached (no superview), not selected, not hidden, have no animations, and don't hold the first responder. All of them sit in the **Files** outline's `_rowViewPurgatory`. It grows only inside `scrollRowToVisible` when Return in Find File jumps far down the tree (y 0 → 2,325), by 7–9 rows each time.
- The AppKit mechanism, from disassembly (`step1a/rowdata.asm`, macOS 26.6):
  - `updateVisibleRowViews` (the tile after a scroll) turns on `_rowViewPurgatoryEnabled`. Rows leaving the view then go into the purgatory set and the reuse queue, rather than being removed and queued.
  - The only removal from the set is `removeObject:` in `_preparedRowViewForRow:storageHandler:`, which runs when the delegate hands that same row view out again.
  - The end-of-tile flush detaches leftovers but never empties the set. Only `dealloc` releases it.
  - `reloadData` (through `purgeRowViewData` → `clearReuseQueue`) empties the reuse queue. Something else does too during a review switch (the pool dropped to 0 on Older Commit even with `reloadItem(nil, reloadChildren: true)`, which doesn't purge). After that, nothing will ever hand those rows out again.
  - A global gates the purgatory, which is why the bare command-line probes never reproduced it.
- So any reuse left to AppKit's queue leaks on this OS. With our own spare list fed by `didRemove`, every parked row is handed out again. In the census, live rows sat at **54 every cycle**, purgatory at 0, and TreeCells rose and fell with the tree (33 ↔ 7) instead of accumulating. I kept `reloadData`. I measured `reloadItem(nil, reloadChildren: true)` too: it didn't help, so it isn't in the commit.

## What didn't hold

- **Inspector.merge wasn't part of the leak.** Its purgatory stayed at 0 throughout and its rows were flat. The mismatch was real (children replaced, then `removeItems`, in up to four separate updates), and I fixed it on its own. All the leak was in the Files outline (and could be in Find's).
- **"Reuse row views the way NSTableView intends" isn't enough on macOS 26.6** (above). The commit reuses rows, but through our own spare list, not the table's queue.
- **The busy dip never reaches zero in practice.** `open()` holds `busy` for the whole load, so the spin's -1/+1 never fired idle waiters early. The spin itself was real.
- The plan says the identifier scan "runs on main when the caret lands". With tokens it was quadratic. Without tokens (the minified open, before analysis) it was linear, but 337 ms of `CharacterSet` per landing.
- Tokens from `tokensPerLine` are already sorted per line. `OrderedIntersections` checks that and sorts only if not.

## What the next step must know

- **The forward guard.** The first nine GUI runs were clean. Then from about 16:50 to 17:20, 11 runs were killed as "came in front", from 1 s to 8 s after launch, and every one had `lsappinfo front` naming the benchmark's own pid. That included the first after-quick and soak attempts, and all the killed runs are in `step1a/guard-kills/`. All of the killed runs were new builds, so I checked the old app under the same conditions. No saved application state existed. The kills stopped on their own: back-to-back launch+reading runs of the old and new apps were clean, then the full quick tier and the 100-cycle soak ran without a kill. My guess is that the person at the machine closing or switching away from their front app made macOS bring the next app in window order forward, but I didn't verify it. Re-run a killed run rather than debugging it.
- **The reading scenario beeps 67 times on every build** (`key w` / `key j` step past the end of a short file). Its `beeps` budget fails with or without these changes. The script needs fewer steps or a longer file.
- **`patho` can't measure the identifier fix.** Every pathological run still dies at 4 GB. Use `step1a/tools/minprobe.sh` with an app re-signed with `get-task-allow` (`tools/debuggable.plist`) to sample the main thread.
- `heap`, `leaks` and `sample` attach to the ad-hoc signed app only in a restricted mode. For stack attribution, re-sign a scratch copy with `get-task-allow`. Never ship it.
- The scroll-pocket/KVO growth above is the remaining soak drift (0.3 MB/cycle). Step 3's glass work is the natural home for it.
- Hidden expectations in the new code: callers of `forEachIdentifier` must pass tokens relative to the line start (as `tokensPerLine` makes them). `RowViews.next()` must be the only source of row views for a list that reports `didRemove` to it.
