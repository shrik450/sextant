- **d20a273, bf91c94, eaedc79, 1b72116: keeping benchmarks from disturbing the person at the machine** (see below).

Fixtures: `audit2/fixtures` was moved to `scratch/perf/fixtures` (a real directory, since symlinked roots would hit the canonicalisation bug); `audit2/fixtures` links back. ## Probe: before and after
The same program sleeps its main queue 300 ms, then 2 s, then 10 s, and is killed 1.5 s into the 10 s stall:
- Old probe: max wait 2005 ms. The stall it died in doesn't show.
- New probe: 303 / 2004 ms finished, **1531 ms in flight at the kill**. In the app (`stall` command), 1997 ms finished and **2059 ms** when killed 2 s into a stall.
These checks are the `probe` scenario's budgets and run in every quick tier.

## What didn't hold, or surprised me
- **The benchmarks disturbed the user.** Under `--background`, Go to Anything's panel floated over every app: it's a floating panel, and it never hid because the app was never active. Opening a repository again, and jumping, ordered the window front. Every `NSSound.beep()` sounded, and the soak beeped about 10 times per cycle: after cycle 1 it sat in the overview, where Next and Previous File refuse. AppKit also beeped for keys nothing handled; Command-Return to the jump bar never reached it, which is also why **worktrees opened 1 pane, not 5**. The audit's five-pane run had the same problem (its dump came back empty).
  - Fixes: `NSWindow.raise()`; a jump bar at normal level when the app runs behind; `beep()` and AppKit's unhandled-key bell go to the automation log under a background script; keys for the jump bar go straight to it; the soak starts each cycle from the first file.
  - Guard: the harness kills the app if `lsappinfo front` reports it as the front app or one of its windows sits above the normal level. Every scenario has `beeps <= 0` and `came_forward <= 0` budgets (`*` rows in `budgets.tsv`).
  - The user asked me to stop GUI runs, so **these fixes aren't verified in a run** past one goto-work run (0 forward, 0 beeps) and one worktrees run (0 forward, 0 logged beeps, but that run still rang AppKit's bell; eaedc79 came after it).
- Linux edits 5 s apart conflated: edit 1's refresh was still in `for-each-ref … ahead-behind` when edit 2 arrived, so edit 1 showed only with edit 2 (`edit_correct_min 0`). This is the audit's F6, not a lost update. The scenario now spaces edits 10 s apart, and Refresh is timed by what it starts: inside `measure` the debounced refresh hadn't begun, so it measured 0 gits. **The baseline's Linux edit and refresh numbers come from before this change.**
- worktrees: even with one pane showing wt-4, staging in wt-2 ran `status` 19 times there and **76 times in the other four worktrees**.
- Lookups were 2.6× slower than in the audit, likely contention from the load average.

## What the next step must know
- Run `nix develop -c Tests/perf/run.sh quick` (set `SEXTANT_PERF_BUNDLE` to your bundle ID). `run.sh <scenario>` runs one scenario; `run.sh report <dir>` reprints a table. Results go to `scratch/perf/<commit>-<what>-<time>/`, unless you pass `--out`.
- **Before trusting any GUI run, check `beeps` and `came_forward` are 0.** Re-run worktrees, soak and linux into `baseline/full` once the user allows GUI runs again (about 15 min: `run.sh --out …/baseline/full worktrees soak linux`, then `run.sh report …/baseline/full`). The `beeps`/`came_forward` rows for the rest of `full` are missing because those runs predate them.
- The `watch` poll and the probe cost a little main-thread time. Idle runs without the probe. The automation's `beginActivity(.latencyCritical)` disables App Nap.
- Patho runs stop at 4 GB (`--max-mb`). Once step 2 bounds them, they'll get through and report time-to-show and CPU after leaving.
- Budgets come from the audit's §4, with astra's and argon's §4.4 corrections, each cited in the `why` column. Memory budgets for glass add argon's 75 MB to astra's classic figures (225 MB steady / 325 MB peak). That's my call; change it if you want classic runs instead.
